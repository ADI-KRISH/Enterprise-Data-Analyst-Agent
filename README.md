# Enterprise Data Analyst Agent

Ask a business question in plain English; get a grounded answer, the SQL that produced it, the data, and a chart.

> **All data is synthetic.** The database is generated by `database/seed.py` (fixed seed, Indian retail, INR). It does
> not describe any real company. Injected patterns (so "why" questions have answers) are listed in
> [`database/SEED_NOTES.md`](database/SEED_NOTES.md). This is a working prototype, **not a production deployment**.

## How it works

```
question → understand → retrieve (schema + KPI docs) → clarify? ─yes→ ask the user
        → plan → generate SQL → validate ⟲ → execute (read-only) → verify ⟲
        → analyze (Pandas) → chart (Plotly) → respond → grounding check ⟲ → answer
```

| Guarantee | How |
|-----------|-----|
| **No invented numbers** | The responder only sees executed results + deterministic Pandas analysis. `agents/grounding.py` extracts every number from the answer and checks it against those values (tolerating rounding, %, lakh/crore). Ungrounded answers are regenerated once, then returned with `grounded: false`. |
| **Read-only DB** | Agent connects as `analyst_ro` (SELECT on schema `analytics` only; `statement_timeout=15s`, `default_transaction_read_only=on`). Admin credentials are used only by `database/seed.py`. |
| **Validated SQL** | `agents/sql_validator.py` (sqlglot): one SELECT/WITH statement, no DDL/DML/`pg_*`/comments with statements, tables and columns must be in `database/allowlist.yaml`, `LIMIT` enforced, then an `EXPLAIN` dry-run before execution. |
| **Clarify, don't guess** | Undefined metrics (e.g. churn), unknown entities or out-of-scope questions get a clarification question instead of an answer. |
| **Anchor date** | "Last quarter", "this month", … resolve against `ANCHOR_DATE = max(order_date)`, not the system clock (see `retrieval/docs/reporting_policies.md`). Quarters/years are Indian fiscal (Apr–Mar). |

## Quick start

Requires Python 3.11 and Docker (for PostgreSQL 16).

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # set passwords + OPENROUTER_API_KEY

docker compose up -d db         # PostgreSQL; creates schema + the analyst_ro role on first start
docker compose run --rm seed    # or: python -m database.seed   (generates ~50k synthetic orders)
python -m retrieval.build_index # optional: pre-build the vector index (downloads a small embedding model once)

uvicorn app.main:app --reload             # API   → http://localhost:8000/docs
streamlit run dashboard/streamlit_app.py  # UI    → http://localhost:8501
```

Or run everything in containers: `docker compose --profile app up -d --build` (after `docker compose run --rm seed`).

Retrieval uses ChromaDB + local `fastembed` embeddings. If the embedding model can't be downloaded (offline /
restricted network), `RETRIEVAL_BACKEND=auto` falls back to lexical (TF-IDF) search; set `RETRIEVAL_BACKEND=lexical`
to skip the download attempt.

### LLM provider

OpenRouter via `langchain-openai` (`app/llm.py`). Defaults are free-tier models (`LLM_MODEL_STRONG` for planning and
SQL, `LLM_MODEL_FAST` for understanding/clarifying/answering, each with `LLM_MODEL_FALLBACK`). Free models can be slow
or rate-limited (HTTP 429 is retried with backoff); set paid models in `.env` for lower latency. Every LLM call is
recorded in the response `trace`, including which model actually answered.

## API

`POST /analyze` with `{"question": "..."}` returns:

```json
{"answer": "...", "sql": "...", "data": [...], "columns": [...], "visualization": {"data": [], "layout": {}},
 "analysis": {...}, "grounded": true, "needs_clarification": false, "clarification_question": null,
 "trace": [...], "latency_ms": 0, "error": null}
```

Also `GET /health` and `GET /schema`. Every request is appended to `logs/audit.jsonl` (question, SQL, validation
result, row count, latency, grounded).

## Tests and evaluation

```bash
pytest -q               # unit tests; DB-backed tests are skipped if PostgreSQL isn't up and seeded
python -m eval.run_eval # runs eval/questions.yaml (gold SQL + must-clarify cases) through the real agent
```

`eval/run_eval.py` writes timestamped results to `eval/results/` (git-ignored). **This README quotes no accuracy or
latency numbers**: run the evaluation yourself, with your own model configuration, to get them. Scoring is
execution-match against gold SQL, clarification recall / false-clarification rate, grounded rate and latency.

## Layout

```
app/            FastAPI (main.py), LangGraph pipeline (graph.py), state, config, LLM client (llm.py), audit log
agents/         understand, clarifier, planner, sql_generator, sql_validator, executor, verifier, responder, grounding, dates
retrieval/      docs/ (KPI definitions, data dictionary, reporting policies), build_index.py, retriever.py
database/       schema.sql, roles.sql, seed.py, allowlist.yaml, SEED_NOTES.md
analytics/      deterministic Pandas analysis (growth, share, top-N, period compare, driver breakdown) + formatting
visualization/  chart selection → Plotly JSON
dashboard/      Streamlit UI
eval/           questions.yaml, run_eval.py, results/
tests/
```

## Limitations

- Synthetic data only; the KPI definitions are documented assumptions, not a real company's.
- The grounding check verifies that numbers appear in (or follow by rounding from) the result; it cannot verify that a
  sentence interprets them correctly. "Why" answers show *where* a metric moved, not proven causes.
- SQL quality depends on the configured LLM; the validator and verifier guard safety and obvious failures, not
  semantic correctness.
